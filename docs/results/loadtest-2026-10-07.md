# Load test results (2026-10-07)

## Setup

- Machine: Intel Core Ultra 5 225U, 14 threads, 15.5 GB RAM, Windows 11. k6 runs on the same laptop (a recorded limitation).
- Versions: k6 0.54.0, Toxiproxy 2.9.0, Postgres 16 with pgvector 0.8, Python 3.12; embeddings fastembed bge-small.
- Workload: 3,000 requests, Zipf (seed 11), repeat rate 94.8%, constant arrival rate.
- Stub model: lognormal per model (small 553 / 830 ms, large 748 / 1,429 ms median / p95), seeded (D49).
- Failure runs: 1 in 3 requests skip the cache, so the model faults always meet real traffic (D54).
- Latency budget: p95 2 s (D50). Medians of repeats, with the range in brackets.
- Power: 21 runs on battery, 10 on AC power (power log in the results folder).

## Cold cache: four-way (10 req/s, 5 min)

| Configuration | Runs | p50 | p95 | p99 | Hit rate | Cost / 1k | Errors |
| :-- | --: | --: | --: | --: | --: | --: | --: |
| baseline | 3 | 772 ms (767–773) | 1439 ms (1416–1440) | 1797 ms (1777–1816) | 0.0% | $0.0783 | 0.00% |
| cache_only | 3 | 10 ms (10–11) | 41 ms (39–42) | 1072 ms (919–1074) | 95.4% | $0.0034 | 0.00% |
| router_only | 3 | 730 ms (729–731) | 1405 ms (1403–1442) | 1831 ms (1828–1884) | 0.0% | $0.0742 | 0.00% |
| full | 3 | 10 ms (10–11) | 33 ms (25–50) | 1002 ms (983–1059) | 95.4% | $0.0032 | 0.00% |

**What this shows:** starting from an empty cache, both cache configurations answer 95.4% of requests from the cache (the workload repeats 94.8% of the time, so it fills within the first minute). That takes p95 from about 1.4 s to 33-41 ms and cost per 1,000 requests down by about 96%. p99 stays near 1 s because the remaining 4.6% are misses that go to a model. The router on its own barely moves p95, because the tail is set by the questions it keeps on the large model; its effect is on the small path below.

## Gateway overhead

Embed + cache lookup inside Weir: mean 8 ms (7–27), p95 15 ms (9–161) (cache configurations, all runs).

Container CPU during the cold runs (median of the 5 s samples; 100% = one core):

| Configuration | weir | hospital-rag | postgres |
| :-- | --: | --: | --: |
| baseline | 7% (6–7) | 609% (609–610) | 1% (1–1) |
| cache_only | 609% (608–610) | 0% (0–0) | 2% (2–2) |
| router_only | 7% (6–7) | 608% (607–609) | 1% (1–1) |
| full | 607% (606–607) | 0% (0–0) | 2% (2–2) |

**What this shows:** embedding the question and checking the cache costs Weir about 8 ms on average. The top of the range (27 ms mean, 161 ms p95) comes from the overloaded ramp and the failure runs (backlog M39). Weir reads about 600% CPU whenever the cache is on and 7% without it; most of that is ONNX Runtime's embedding threads spin-waiting rather than useful work (backlog M33). hospital-rag shows the same pattern when it embeds.

## Ramp

![p95 vs request rate](loadtest-ramp.png)

| Configuration | Runs | Highest rate within budget |
| :-- | --: | --: |
| full | 3 | 100 req/s (60–100) |
| baseline | 3 | 60 req/s (60–80) |

**What this shows:** a step counts only if p95 stayed within 2 s, errors within 1%, k6 achieved at least 95% of the target rate and dropped no requests (D61). Full Weir answered at p95 13-42 ms all the way to 100 req/s in 2 of 3 rounds. In round 1, its 80 req/s step started dropping requests (k6 ran out of virtual users because requests were piling up), and at 100 req/s it collapsed: cache lookups timed out under CPU load, 1,832 requests fell through to retrieval and the model, and that extra work pushed p95 to k6's 60 s timeout. Under overload, the cache's safety valve makes things worse (backlog M31). The baseline stays flat at about 1.5 s up to 60 req/s and breaks between 80 and 100. The ceilings differ between rounds because this laptop's capacity did: a 15 W-class CPU at full load for hours, with 21 of 31 runs on battery.

## Spike

A 60 req/s burst for 30 s on a 5 req/s base: peak 10-second p95 22 ms (14–24); the 10-second p95 never left the 2 s budget, so there was nothing to recover from; overall p95 14 ms (12–15).

**What this shows:** a jump from 5 to 60 req/s, held for 30 s, barely registered, because nearly every request was a cache hit.

## Soak

30 min at 10 req/s, first vs last 5 min: p95 13.1 -> 14.6 ms; weir memory 250 MiB at the start, but no memory samples in the last 5 min (docker stats returned nothing); open database connections 19 -> 16; errors 0.00%.

**What this shows:** 30 minutes of steady traffic with no errors and a small p95 rise (13.1 to 14.6 ms, +11%, inside the 20% limit). Memory held at about 250 MiB for the first 25 minutes, but `docker stats` returned nothing for the last 5 (the laptop was short of memory then), so there is no reading to compare and the no-leak check is recorded as incomplete, not passed. Database connections stayed between 16 and 20.

## Failure injection

| Phase | Requests | Model path | Errors | p95 | Fallbacks | Cache bypasses |
| :-- | --: | --: | --: | --: | --: | --: |
| normal | 1797 | 600 | 0 | 1112 ms (1063–1233) | 0 | 0 |
| normal | 1798 | 599 | 0 | 1163 ms (1112–1218) | 0 | 0 |
| large_rate_limited | 1802 | 600 | 0 | 754 ms (752–767) | 541 | 0 |
| normal_2 | 1797 | 600 | 0 | 1155 ms (1073–1194) | 0 | 0 |
| small_timeout | 1792 | 600 | 0 | 1429 ms (1413–1593) | 60 | 2 |
| db_delay | 1791 | 600 | 0 | 1943 ms (1898–2068) | 0 | 1191 |
| recovery | 1815 | 600 | 0 | 1259 ms (1160–1267) | 0 | 0 |

Totals across 3 runs; p95 is the median of the runs. Requests and errors are counted by k6 when each request finishes; model path, fallbacks and cache bypasses come from Weir's request log by when each request started.

**What this shows:** none of the three faults reached users as an error. With the large model rate-limited, Weir sent those requests to the small model (541 fallbacks), and p95 fell to 754 ms because the small model is faster. With the small model timing out after 5 s, the 60 requests routed to it waited for the timeout and then went to the large model; they are about 3% of the phase, so its p95 rose only to 1.43 s. With every database round trip delayed by 2 s, cache lookups timed out and 1,191 requests skipped the cache for retrieval and the model instead: the median p95 was 1.94 s, just inside the 2 s budget, and one run reached 2.07 s. "Model path" counts the 1 in 3 requests that skip the cache by design, so every fault meets real traffic (D54).

**What this shows:** four checks pass. The no-leak check is incomplete, not failed: the p95 half passes, but there are no memory samples for the soak's last 5 minutes. Re-running the 30-minute soak would settle it. Two requests in about 220,000 failed at the connection level (a reset and an EOF): uvicorn's 5 s keep-alive timeout racing k6's connection reuse. They count as errors and round to 0.00% (D60, backlog M32).

## Limitations

- The model is a stub with realistic timing, not Groq: answers are real retrieval, generation is simulated.
- k6, Weir, hospital-rag and Postgres share one laptop; one Weir process (no horizontal scaling).
- Rates are modest by design (a free-tier, single-machine project); the ramp finds this machine's limit.
- CPU readings include ONNX Runtime's embedding threads spin-waiting between requests, so a container that embeds (weir with a cache, hospital-rag) reads far above the work it does.
